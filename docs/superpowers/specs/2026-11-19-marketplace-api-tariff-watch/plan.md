# План задачи 24: тарифы WB и Яндекс Маркета

**Спецификация:** [spec.md](spec.md), утверждена владельцем 2026-11-19.
**Режим:** реализация в текущей изолированной ветке `feature/task-23-official-sources`; без push, настройки Coolify и production-развёртывания.

## Границы

Только Seller/Partner API для чтения доступных тарифных сведений. Новости продолжают поступать из существующих официальных источников. Новый источник сравнивает тарифные снимки по расписанию текущего цикла и создаёт проверяемую находку с карточкой влияния только при фактической дельте. Расчёты тарифов Яндекса маркируются как оценочные. Запросы к модели для дельт не добавляются.

## Шаги реализации

### 1. Закрепить контракт API и безопасные настройки

- Сверить методы WB, поля тарифных ответов, токен-категорию и лимиты по официальной актуальной OpenAPI-схеме до реализации клиента.
- Для Яндекса использовать официальные методы `GET /v2/campaigns`, `POST /v2/businesses/{businessId}/offer-mappings` (с постраничным чтением) и `POST /v2/tariffs/calculate` (пакеты до 200 предложений; подтвердить лимит по схеме).
- Использовать отдельные переменные окружения `WB_SELLER_API_KEY` и `YANDEX_MARKET_API_KEY`; реальные значения остаются в защищённом источнике и не выводятся в терминал, журналы, тесты или Git.
- При недостаточных правах или отсутствующих параметрах продукта сохранять безопасный статус источника, не подменять его нулевым тарифом.

### 2. Реализовать изолированные API-клиенты

- Добавить `collector/wildberries_api.py` и `collector/yandex_market_api.py` с таймаутом, ограничением ответа, проверкой HTTPS/хостов, страниц и схемы, безопасными кодами ошибок.
- Нормализовать только необходимые значения для сравнения: кабинет/кампания, товар или склад/категория, модель продаж, вид услуги, число и единица тарифа, дата действия при наличии.
- Не делать ни одного метода записи. Не включать webhook или настройки кабинета.

### 3. Добавить снимки и детерминированное сравнение

- Добавить в `db/schema.sql` таблицу нормализованных снимков с уникальным устойчивым ключом и временем получения; не сохранять полный ответ API или секреты.
- Реализовать атомарную запись успешного снимка и сравнение с предыдущим успешным снимком той же площадки.
- Первый снимок — только базовый. Ошибочный, неполный или пустой ответ не должен заменять последний успешный снимок.
- Повтор неизменившихся данных не создаёт новую дельту; изменения группируются по площадке и услуге, с группировкой по складу/кампании.

### 4. Создавать находки и карточки влияния

- Для каждой новой группы дельт создавать один русский исходный материал, детерминированную находку и карточку `needs_review` в одной транзакции.
- В тексте показывать старое и новое значения, количество затронутых предложений при расчёте Яндекса, максимальную/сводную разницу и время наблюдения. Не выдавать примерный расчёт за фактическое списание.
- Привязывать `change_type` к тарифной услуге, выбирать только очевидный процесс склада; точную связь/последствия оставлять владельцу на подтверждение.
- Использовать ключ идемпотентности, чтобы повторный цикл или повторная вставка не создавали дубли. Не отправлять синтетический материал на перевод и модельную классификацию.

### 5. Подключить сборщик и документацию

- Заменить один общий обработчик `kind=api`, который сейчас направляет API-источники в Ozon, на явную маршрутизацию по `source.code`.
- Добавить отдельные официальные источники WB и Яндекса в `config/sources.json`; отсутствие/ошибка одного API не блокирует остальные источники.
- Обновить `README.md`, `progress.md`, `kanban.md`, SPEC и чек-лист. Сохранить проверяемый статус: локально реализовано, push/deploy не выполнены.

### 6. Проверить и зафиксировать

- Свежий тестовый исполнитель пишет фикстурные тесты до основной реализации; автор реализует код после подтверждённого RED.
- Тесты покрывают авторизацию/ошибки, пагинацию, лимиты батчей, нормализацию, baseline, сравнение, дубль, частичный отказ, отсутствие ключей и транзакцию находки/карточки.
- Отдельный свежий тестовый исполнитель запускает целевые проверки и один полный набор проекта на изолированной БД. Полный набор не дублировать в основном потоке.
- После успешной проверки сделать один локальный коммит `feat(24): monitor WB and Yandex tariff changes`. Push и deployment не входят в задачу.

## Риски и решения

- WB OpenAPI может менять конечные методы, права токена и частоту обращений; код фиксируется только после проверки текущей первичной схемы.
- У Яндекс Маркета калькулятор даёт оценку; отсутствующие параметры ассортимента исключаются из расчёта с отдельной диагностикой.
- Изменение API-тарифа не всегда означает вступление в силу немедленно. Если дата действия не возвращена явно, карточка показывает только время наблюдения.
- Снимки могут охватывать большой ассортимент. Запросы пакетируются, а база хранит только значения, необходимые для последующего сравнения.

## Критерий завершения

Тесты подтверждают, что ключи только читаются из окружения, первый снимок не даёт ложных уведомлений, фактическая тарифная дельта один раз создаёт на русском языке находку и карточку владельца, а сбой одного API не останавливает сбор новостей и второго API. Состояние production не меняется.
