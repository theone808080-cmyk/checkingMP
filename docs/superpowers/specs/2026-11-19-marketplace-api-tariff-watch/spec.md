# SPEC: мониторинг изменений тарифов Wildberries и Яндекс Маркета через API

**Статус:** утверждена владельцем 2026-11-19; реализация выполнена локально, production-проверки не проводились.
**Номер задачи:** 24.

## Цель

Подключить read-only API кабинетов Wildberries и Яндекс Маркета к checkingMP, чтобы отслеживать изменение стоимости услуг для доступного ассортимента и показывать подтверждаемые карточки влияния на склад. API не используются как поток общих новостей и не заменяют официальные новостные источники.

## Пользовательский сценарий

При плановом цикле сервис получает актуальные тарифные данные площадок, сохраняет исходный снимок и сравнивает его с предыдущим. Первый снимок становится базовым и не создаёт находки. Если тариф или комиссия для товара, услуги либо склада изменились, сервис создаёт одну находку с прежним и новым значением, площадкой, затронутой услугой, временем обнаружения и ссылкой на площадку или метод API. Для неё создаётся карточка влияния со статусом «требует проверки владельца».

## Подключаемые данные

### Wildberries

- Клиент реализован для read-only методов тарифов коробов, монопаллет и комиссий по категориям. Тарифы приёмки и возврата в первую реализацию не включены.
- Официальная техническая OpenAPI-страница WB возвращает ошибку загрузки из среды разработки. Перед production-включением необходимо сверить схему ответов и доступ токена; реальные вызовы WB не выполнялись.
- Сравнивать записи по устойчивому ключу площадка + склад/категория + вид услуги + применимость тарифа.

### Яндекс Маркет

- Получить доступный каталог предложений продавца и необходимые параметры товаров и кампаний. Не рассчитывать тариф для предложения, если обязательных параметров нет; не подставлять догадки.
- Рассчитывать стоимость услуг методом `POST /v2/tariffs/calculate` партиями до 200 предложений. Официальная документация отмечает, что результаты калькулятора приблизительные.
- Цена и габариты товара сохраняются как база сравнения; если эти параметры изменились, полученная разница не создаёт событие об изменении тарифа.
- Сохранять результат как оценку тарифа, а не фактическое списание: документация Яндекса указывает, что калькулятор даёт примерный расчёт.
- В составе сравнения хранить модель продаж, кампанию, товар, услугу, сумму/тип тарифа и доступные параметры расчёта.

## Обработка изменений

1. Использовать расписание существующего цикла; отдельный постоянно работающий процесс и новые обращения к LLM не добавлять.
2. Сохранять нормализованные значения тарифов и время получения в таблице снимков; не сохранять полный ответ API, токены или персональные данные.
3. Нормализовать только поля тарифов, необходимые для сравнения; не считать перестановку полей или изменение метаданных изменением тарифа.
4. Не создавать событие при первом успешном снимке. Создавать его только при подтверждённом различии тарифного значения или параметра услуги.
5. Группировать изменения одного цикла по площадке, складу/кампании и услуге. Для Яндекса включать число затронутых предложений и сводку диапазона изменений; подробные сравниваемые строки хранить в снимках. Повторная идентичная дельта не должна создавать дубль.
6. Создавать находку и карточку влияния детерминированно, без вызова модели. Не придумывать дату вступления в силу: если API её не возвращает, показывать время наблюдения и помечать дату вступления как неизвестную.
7. Указать последствия как факт изменения тарифа и его измеряемую разницу. Связь с конкретными процессами склада остаётся на подтверждение владельцу.

## Доступ и безопасность

- Использовать секреты только из переменных окружения приложения: `WB_SELLER_API_KEY` и `YANDEX_MARKET_API_KEY`. Их production-настройки не проверялись и не менялись.
- Учитывать необходимые идентификаторы кабинетов/кампаний и права только на чтение.
- Не записывать секреты в репозиторий, тесты, трассировки, диагностические сообщения или отчёты.
- Ошибка одного API не должна останавливать сбор новостей и данные другой площадки; показывать безопасный код отказа.
- Не выполнять действия записи в кабинетах, заказах, тарифах, товарах или остатках. Не включать webhooks и не менять настройки кабинета.

## Критерии приёмки

- Без ключа или при отказе API остальные источники checkingMP продолжают работать.
- Первый снимок не создаёт находку; повтор тех же данных не создаёт дубликат.
- Изменение тарифа создаёт одну проверяемую находку с площадкой, услугой, старым и новым значениями, временем наблюдения и связанной карточкой влияния.
- Для расчётов Яндекс Маркета явно отображается, что значение приблизительное; неизвестная дата вступления не подменяется датой получения.
- Ответы с ошибочной схемой или пропущенными полями не превращаются в нулевые тарифы и не создают ложные события.
- Все API-тесты используют фикстуры; отдельный read-only smoke-вызов допускается только после согласованной защищённой настройки ключей.
- Не выполняются push в GitHub, настройка Coolify или production-развёртывание в рамках этой задачи.

## Не входит

- Получение общих новостей, новых правил или официальных публикаций из Seller API.
- Подключение API Ozon повторно, изменение источников Telegram/RSS, сбор заказов/остатков/продаж и любые действия записи.
- Автоматическое применение изменений на складе или автоматическое подтверждение карточки владельца.
