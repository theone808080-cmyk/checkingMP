# Ozon Seller API notifications — implementation plan

> Реализация ограничена одним новым read-only источником. Пользователь одобрил подключение Seller API; наличие доступа к истории сообщений подтверждается только после настройки ключей и рабочего API-вызова.

**Цель:** добавить официальные уведомления Ozon в существующую ленту новостей, не меняя обработку прочих источников.

**Архитектура:** `collector/ozon_api.py` вызывает `/v3/chat/list`, находит только `SELLER_API_NOTIFICATIONS`, затем читает историю через `/v3/chat/history`. Для каждого сообщения создаётся материал с URL, устойчивым по `chat_id` и `message_id`; существующая дедупликация защищает от повторов. Новый тип `api` допускается только в таблице активных источников; кандидаты поиска источников остаются `rss/html/telegram`.

**Секреты:** `OZON_SELLER_CLIENT_ID` и `OZON_SELLER_API_KEY` читаются из окружения. Значения не запрашиваются в чате и не попадают в репозиторий или логи.

## Ограничения

- Только чтение: никаких изменений сообщений, заказов, тарифов, настроек кабинета, webhook или push-подписок.
- Отсутствие ключей отключает только этот источник.
- HTTP 401/403 и ограничения тарифа отображаются как безопасная причина недоступности источника; остальные источники продолжают собираться.
- Не менять модель, промпты, расписание, критерии важности и складские карточки.
- Не включать внешний live-вызов в тесты; тестировать только фикстурами.
- Не отправлять изменения в GitHub и не развёртывать без отдельного поручения.

## Шаги

1. Отдельный исполнитель заменяет устаревшие тесты HTML-архива тестами Seller API и подтверждает RED.
2. Реализовать клиент Ozon с таймаутом, ограничением ответа, заголовками Client-Id/Api-Key, строгим разбором JSON и безопасными категориями ошибок.
3. Реализовать выбор уведомительного чата, разбор сообщений и стабильные URL для дедупликации.
4. Зарегистрировать `ozon_seller_api_notifications` в `config/sources.json`; добавить тип `api` только в ограничение `sources` и валидацию конфигурации, включая миграцию уже существующей БД.
5. В `collector/main.py` подключить API reader без ключей в логах; отсутствие конфигурации помечать как пропуск этого источника, не как ошибку всего цикла.
6. Независимый исполнитель запускает целевые тесты. После этого проверить весь набор один раз на изолированной тестовой БД.
7. Синхронизировать README, Kanban и SPEC; зафиксировать значимую веху в progress.md.
8. Один локальный коммит задачи 23. Push и production deployment не выполнять.

**Критерий приёмки:** без ключей текущие источники продолжают работать; с фикстурами reader выдаёт уведомления только выбранного типа, сохраняет ID/дату, не создаёт повторов; ошибки аутентификации/доступа не прерывают цикл; тесты и миграция проходят.
