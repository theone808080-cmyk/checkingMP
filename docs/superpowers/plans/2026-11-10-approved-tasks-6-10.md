# Утверждённые задачи 6–10: план реализации

> **Для исполнителя:** выполнять последовательно с тестированием по принципу «сначала падающий тест», затем реализация. Рабочая ветка `feature/tasks-6-10` основана на интегрированной ветке задач 2 → 4 → 5.

**Цель:** реализовать утверждённые задачи 6–10 из SPEC.md отдельными проверяемыми коммитами; сначала выполнить утверждённую задачу 3 как необходимую зависимость задачи 9.

**Архитектура:** задача 3 создаёт очередь кандидатов и безопасную проверку источников согласно уже сохранённому плану `2026-11-09-source-discovery.md`. Резервирование оформляется отдельными командами и зашифрованными файлами на постоянном томе, а статусы и трассировка остаются в PostgreSQL и доступны только через текущую авторизацию. Лента получает серверные счётчики для каждой группы фильтров; метаданные доступа расширяют созданные задачей 3 карточки кандидатов; схема потока публикуется как Mermaid-документ.

**Стек:** Python 3.12+, PostgreSQL 17, стандартный HTTP-сервер проекта, `unittest`, текущий Telegram Mini App.

**Спецификация:** `SPEC.md`, задачи 6–10; утверждённая задача 3 является зависимостью задачи 9.

## Общие ограничения

- Одна задача SPEC — один коммит с номером задачи; до каждого коммита запускается весь набор `python -m unittest discover -s tests -q` с отдельной тестовой PostgreSQL через `TEST_DATABASE_URL`.
- Не выполнять автоматическое восстановление поверх рабочей базы. Пробное восстановление создаёт только уникальную временную базу с зарезервированным префиксом и удаляет только её.
- Не хранить секреты, дампы, полные запросы и ответы модели, полные тексты публикаций или личные данные в Git, журнале и API-ответах.
- Все API и страницы с техническими данными требуют Basic Auth или действующую сессию владельца Telegram; изменяющие действия очереди кандидатов требуют Basic Auth и same-origin защиту.
- Перевод, оценка релевантности, важность, сортировка и доставка уведомлений не меняются.
- Не включать внешние платные сервисы, обход авторизации или изменения на сервере и в Coolify.

## Области риска для проверки

- Отказ дампа, неверный ключ шифрования, пустая/усечённая копия и ошибка восстановления не должны помечать backup успешным.
- Восстановление допускается только в автоматически созданную тестовую БД; URL рабочей БД и пользовательские БД не должны попадать в удаляющий путь.
- Трассировка не должна сохранять сырые исключения, промпты, ответы модели или публикации; история повторов остаётся неизменной.
- Счётчики фильтров не должны зависеть от лимита страницы и учитывают все остальные выбранные группы, исключая собственную группу.
- Синхронизация статических источников не должна перезаписывать ручные кандидаты и одобренные поля задачи 9.
- Диаграмма явно отличает интегрированное поведение от запланированных возможностей и не раскрывает инфраструктурные секреты.
