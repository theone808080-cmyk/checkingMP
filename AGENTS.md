# Инструкции проекта

## Документы и память

- `README.md` — обзор продукта, устройство кода, архитектура, навигация по папкам и ключевым файлам, настройка и команды.
- `progress.md` — только важные вехи, проверенные результаты, решения и следующий шаг.
- `prd.md` — Product Requirements Document: описание продукта, пользователей, целей, сценариев и показателей успеха. Перед созданием или существенным изменением PRD сначала опросить владельца.
- `kanban.md` — бэклог и идеи. Реализацию планировать из согласованных записей Kanban и SPEC; синхронизировать статусы задач.
- `SPEC.md` — утверждённые требования. История развития процесса и структура проектных документов описана в этом файле; новые функциональные спеки размещать отдельно.
- На момент добавления этих правил `prd.md` и `kanban.md` в рабочей копии отсутствуют. Не описывать их как существующие до создания.

## Процесс разработки: SDD

Работать по spec-driven development (SDD): PRD → функция → интервью владельца → спецификация → план → задачи → код.

1. Перед написанием спецификации выяснить назначение функции, пользователей, KPI, сценарии, ограничения и критерии приёмки. Задать владельцу необходимые вопросы.
2. Для каждой новой функции создать отдельную папку в `docs/superpowers/specs/` или другом согласованном каталоге. В ней хранить спецификацию (`spec`), план (`plan`) и задачи (`tasks`); синхронизировать задачи с `kanban.md`.
3. Сначала показать владельцу спецификацию. План, задачи и код создавать только после явного одобрения спецификации.
4. Не писать код для функциональности, которой нет в одобренной спецификации. Если реализация требует отклонения от неё, сообщить владельцу до коммита и получить решение.
5. Одна задача из SPEC — один коммит. В сообщении коммита указывать номер задачи. Не объединять разные задачи в одном коммите.
6. Для каждой задачи должны быть тесты. Их разрабатывает отдельный агент, отличный от автора кода; тесты запускает отдельный агент. Перед каждым коммитом запускать весь набор тестов и сообщать результат.
7. Не включать в Git ключи, токены, пароли, рабочие данные или тестовые секреты. Использовать безопасные заглушки и локальную конфигурацию.
8. Не выполнять push, развёртывание или изменения внешней инфраструктуры без отдельного явного поручения владельца.

## Работа с кодовой базой

- Сначала прочитать `README.md`, `progress.md`, соответствующие разделы `SPEC.md` и актуальные план/задачи.
- Проверять состояние Git и сохранять чужие изменения. Для параллельной работы применять отдельные ветки или рабочие копии.
- Использовать команды тестирования, указанные в README и плане задачи; не считать пропущенные интеграционные тесты пройденными.
- Обновлять `README.md` при изменении архитектуры, навигации, команд или заметных артефактов; обновлять `progress.md` только при значимой вехе.
