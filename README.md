# Радар маркетплейсов и «Честного Знака»

Пилот для мониторинга публичных изменений Ozon, Wildberries, Яндекс Маркета и «Честного Знака» по бытовой химии. Подготовлена гибридная схема размещения; фактическое развёртывание не выполнено.

```text
источники → collector → PostgreSQL → очередь ручного разбора → PostgreSQL → web
```

Railway предназначен для сбора, PostgreSQL и защищённой веб-страницы; локальный LM Studio — для обработки по ручному запуску через защищённый API. Без настроек API `process` работает непосредственно с локальной PostgreSQL. Локальный пилот также поддерживает ручной экспорт `prepare-review` и импорт проверенных сигналов.

## Структура

| Путь | Назначение |
|---|---|
| `config/sources.json` | Реестр публичных источников и их уровень доверия |
| `collector/` | Получение RSS, публичных HTML-лент и Telegram preview |
| `worker/` | Явный запуск ограниченной партии через локальный LM Studio |
| `db/` | Схема PostgreSQL и операции очереди/сигналов |
| `web/` | Локальная страница с фильтрами и состоянием источников |
| `work/` | Временные экспортированные партии ручного разбора (не коммитятся) |
| `Dockerfile` | Общий образ web и разового collector для Railway |
| `docs/holst-board-text.md` | Подготовленный текст для обновления доски Holst |

## Первое получение на Linux-сервере (инструкция на будущее)

Linux-сервер, провайдер и способ постоянного запуска ещё не выбраны. Это пример ручной подготовки, а не выполненное развёртывание; подставьте URL публичного репозитория после публикации. На сервере нужны Git и Python 3.12 или новее. Убедитесь, что `python3 --version` показывает версию не ниже 3.12: ниже в примере используется команда `python3`, доступная для выбранной совместимой версии. Для веб-режима также потребуется отдельно подготовленная база PostgreSQL и её строка подключения.

```sh
git clone <PUBLIC_REPOSITORY_URL> marketplace-compliance-radar
cd marketplace-compliance-radar
cp .env.example .env
chmod 600 .env
# Отредактируйте .env на сервере, не добавляя секреты в Git.
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
set -a
. ./.env
set +a
.venv/bin/python main.py web
```

Команда запускает веб-процесс в текущем терминале; она не настраивает службу, контейнер, расписание или перезапуск после выхода. Для отдельного однократного сбора выполните `.venv/bin/python main.py collect` в том же окружении. Не публикуйте `.env` и не добавляйте реальные значения в документацию или коммиты. До открытия внешнего доступа отдельно настройте HTTPS и подходящий способ управления процессом.

Файл `.env` загружается командой `.` как POSIX shell-код, поэтому записывайте значения в виде обычных shell-присваиваний и заключайте каждое значение в одинарные кавычки, например `DATABASE_URL='значение'`. Внутри одинарных кавычек символы `$`, обратная кавычка и `#` не раскрываются и не начинают комментарий. Если в значении есть апостроф, используйте POSIX shell-запись вида `VALUE='часть'\''часть'`, которая безопасно соединяет фрагменты со значением апострофа между ними. Не вставляйте в файл команды или конструкции `$(...)`; не включайте трассировку shell (`set -x`) при загрузке файла, чтобы не раскрыть значения в терминале. Сохраняйте права `600` на `.env`.

## Подготовка

Нужен Python 3.12+. Для локального режима также нужен PostgreSQL: создайте базу `marketplace_radar`, скопируйте `.env.example` в `.env` и задайте строку подключения в окружении. Для обработки через HTTPS локальная PostgreSQL не требуется.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Переменные из `.env` загружаются командной оболочкой перед запуском. В PowerShell для пилота можно задать их в текущем окне:

```powershell
# Задайте DATABASE_URL в окружении локально, не сохраняя секрет в Git.
```

## Ручной цикл

Для обработки через LM Studio запустите его локальный сервер, загрузите модель и задайте в PowerShell имя модели из ответа `/v1/models`:

```powershell
$env:LM_STUDIO_MODEL = 'имя-загруженной-модели'
.\.venv\Scripts\python.exe main.py health
.\.venv\Scripts\python.exe main.py process
```

По умолчанию используется `http://127.0.0.1:1234/v1`, размер партии — 10 (допустимо 1–50), тайм-аут — 120 секунд. Параметры `LM_STUDIO_BASE_URL`, `LM_STUDIO_MODEL`, `LM_STUDIO_TIMEOUT` и `LM_STUDIO_BATCH_SIZE` можно задать в окружении; `.env` автоматически не загружается. `health` проверяет `/models`, но не запускает обработку. При недоступности сервера или некорректном ответе статусы очереди сохраняются. Сигналы модели требуют проверки человеком. Одновременные запуски `process` не координируются; запускайте только один процесс за раз.

```powershell
.\.venv\Scripts\python.exe main.py collect
.\.venv\Scripts\python.exe main.py prepare-review
.\.venv\Scripts\python.exe main.py web
```

После `prepare-review` файл `work/pending-review.json` передаётся агенту вместе с командой «обработай новости». Агент создаёт `work/reviewed-signals.json`, после чего примените его:

```powershell
.\.venv\Scripts\python.exe main.py import-review work\reviewed-signals.json
```

Структура импортируемого файла приведена в `config/reviewed-signals.example.json`. Значение `severity` допускает только `critical`, `important` или `info`, а `verification` — `confirmed` либо `needs_check`. В `skipped_material_ids` попадают нерелевантные материалы, чтобы они не возвращались в следующую партию.

Откройте `http://localhost:8000` с настроенными учётными данными Basic. Команда `python main.py health` проверяет локальную PostgreSQL и LM Studio; это не проверка удалённого API.

## Границы пилота

Система читает только публичные источники. Она не входит в кабинеты, не обходит защиту сайтов и не выполняет действий на маркетплейсах. Сигнал — это черновой вывод для проверки человеком, а не юридическое заключение.

## Подготовка Railway

Это инструкция на будущее: аккаунт, репозиторий, проект, база, домен, расписание и лимиты не создавались. Для двух сервисов выберите один и тот же публичный репозиторий и один `Dockerfile`; настройки задаются отдельно в Railway. Веб-сервис запускает `python main.py web`, collector — `python main.py collect`. Последний выполняет один проход и завершает процесс, а не работает постоянно. В настройках collector задайте Cron Schedule `0 6,18 * * *`: это 06:00 и 18:00 UTC, или 09:00 и 21:00 МСК; возможна задержка запуска. Не задавайте HTTP healthcheck для collector. Для web укажите `/health`: ответ 200 означает, что процесс может выполнить `SELECT 1`, а 503 — что база недоступна; это не проверка модели или качества сбора. Railway передаёт `PORT`, приложение слушает все интерфейсы.

Переменные Railway без значений:

| Сервис | Имя | Назначение |
|---|---|---|
| web, collector | `DATABASE_URL` | Reference variable на `DATABASE_URL` сервиса PostgreSQL в том же проекте и окружении, через частную сеть |
| web | `WEB_BASIC_USER` | Имя пользователя HTTP Basic |
| web | `WEB_BASIC_PASSWORD` | Надёжный уникальный пароль HTTP Basic |
| web | `WORKER_TOKEN` | Отдельный случайный секрет для API обработчика |
| web | `PORT` | Предоставляется Railway; вручную не задавать без необходимости |

Для обоих сервисов выберите ссылку на переменную базы в интерфейсе Railway, а не копируйте строку подключения. Базу не открывайте в публичную сеть. Учётные данные задаются только в Variables, не в репозитории или примерах; передавайте Basic и токен только по HTTPS. Веб-страница требует Basic Auth, а `GET /api/worker/pending` и `POST /api/worker/results` требуют отдельный Bearer-токен. Локально задайте `WORKER_API_URL` как HTTPS origin веб-сервиса без пути и `WORKER_TOKEN` как тот же секрет, что на web. Команда `process` получит партию через API, обратится к локальному LM Studio и отправит результат обратно. При задании только одной из этих переменных запуск завершается ошибкой; без обеих используется локальная база. Переменные `LM_STUDIO_*` нужны локальному процессу и не задаются в Railway для запуска модели. При неизвестном результате отправки проверьте очередь перед повторным запуском.

В Workspace Usage запланированы предупреждение о расходе Compute Usage на $3 и жёсткий лимит на $5 за расчётный период. При достижении лимита Railway останавливает рабочие нагрузки; это не гарантия общего счёта или отсутствия задержки учёта. Доступность и условия лимита проверьте перед запуском. После пробного периода проверьте поддержку cron и стоимость на выбранном тарифе: не предполагайте, что расписание продолжит работать автоматически на бесплатном плане. Ограничения пробного доступа к исходящей сети также могут мешать сбору.

Справка Railway: [cron](https://docs.railway.com/cron-jobs), [PostgreSQL](https://docs.railway.com/databases/postgresql), [лимиты расходов](https://docs.railway.com/pricing/cost-control), [пробный период](https://docs.railway.com/pricing/free-trial).

# Защищённый API обработчика

Веб-сервер слушает порт `PORT` на всех интерфейсах. `GET /health` доступен без авторизации; остальные страницы требуют HTTP Basic с переменными `WEB_BASIC_USER` и `WEB_BASIC_PASSWORD`. Для `/api/worker/` нужен отдельный токен `WORKER_TOKEN` в заголовке `Authorization: Bearer …`. Если соответствующие переменные не заданы, доступ запрещён.

`GET /api/worker/pending?limit=10` возвращает объект с массивом `materials`; допустимый размер партии — от 1 до 50. `POST /api/worker/results` принимает JSON с `batch_material_ids`, `signals` и `skipped_material_ids`. Авторизованный обработчик передаёт идентификаторы обработанной партии; перед импортом сервер блокирует записи и проверяет, что они существуют, уникальны и всё ещё ожидают обработки. Состав сигналов проверяется по этой партии, а невалидный или устаревший результат отклоняется без импорта. Одновременный запуск CLI и HTTP-обработчика не поддерживается: запускайте их по очереди. Переменные доступа задаются только во время запуска; передача учётных данных должна происходить через HTTPS.
